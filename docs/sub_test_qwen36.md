# Sub-test: Cross-Model Validation (qwen3.6)

*Thesis sub-test — clearly labeled and documented.*
*Date: 2026-05-07.*

---

## 0. Why this sub-test exists

The main thesis evaluation (the **n20 baseline run**, completed
2026-05-05) used a single base model:

> **qwen3:30b-a3b-instruct-2507-q4_K_M** — Qwen3 30B A3B Instruct,
> Q4_K_M quantization, ~18.6 GB.

The methodology produced a clean per-project verdict on 10 hand-
curated projects: 4 strongly-positive, 2 strongly-negative, 4
null. The status report and presentation correctly note this is
*conditional on the model used*.

This sub-test **directly tests that conditionality** by re-running
the same multi-run paired methodology on a **representative
4-project subset** under a **different, stronger base model**:

> **qwen3.6:35b-a3b-coding-mxfp8** — Qwen 3.6 35B A3B Coding,
> mxfp8 quantization, ~37.7 GB. Newer generation, larger total
> parameter count, coding-specialized post-training.

If the per-project verdict pattern (helps / hurts / null) **survives
the model swap**, that is strong evidence that the methodology
identifies a real project-level property — not a model-specific
artefact. If the verdicts **shift**, that is also informative: it
quantifies how much of the "RAG benefit" measured in the n20 run
is intrinsic to the project versus mediated by the chosen base
model.

---

## 1. Research question (sub-test only)

> Does the per-project RAG-helps-vs-hurts pattern observed under
> `qwen3:30b-a3b-instruct-2507-q4_K_M` generalise to a different,
> stronger base model (`qwen3.6:35b-a3b-coding-mxfp8`)?

This is a **cross-model validity** question. It is *not* about
which model is better in absolute terms; it is about whether the
methodology's per-project verdicts are model-invariant.

## 2. Project subset and rationale

The sub-test runs on **4 projects** out of the 10 in the baseline,
chosen one-per-category to make the comparison interpretable:

| Project | n20 baseline d_z | n20 baseline p | Why selected |
|---|---|---|---|
| **keycloak** | +1.54 | 0.0002 | The anchor — strongest reproducibility (3 independent pilots agree). If the verdict survives the model swap here, it survives anywhere. |
| **mastodon** | +1.69 | 0.0002 | Strongest absolute positive on a *small* KB (10 chunks). Tests whether the small-KB-large-effect pattern is model-specific. |
| **mattermost** | −0.99 | 0.0007 | Strongest negative. Tests the most interesting hypothesis: does a coding-specialised model *fix*, *reverse*, or *amplify* the RAG-hurts pattern? |
| **bitwarden** | +0.03 | 0.97 | The null with the highest baseline F1 (0.13) — direct test of the "stronger LLM = less RAG headroom" hypothesis. If qwen3.6 raises baseline floor further, RAG headroom should shrink to or below zero. |

Why not all 10? Compute: a single project at N=20 takes ~1–3 hours
on the larger model. 4 projects ≈ 6–12 hours. 10 projects ≈ 24 hours.
The 4-project subset is sufficient to test the methodology's
cross-model validity claim while leaving budget for future
predictor-study extensions.

## 3. Methodology (identical to baseline)

* Multi-run paired statistics, **N=20 paired runs per project**.
* Per-story Wilcoxon (PRIMARY) + paired t-test (sensitivity) +
  Shapiro-Wilk normality + paired Cohen's `d_z`.
* Same `EvaluationPipeline.run()` codepath, same retriever, same
  vectordb cleared and re-ingested per project from that
  project's own docs.
* **Only the `--model` flag changes** between the baseline and
  this sub-test. Everything else is held constant.

## 4. File and naming conventions

The driver was originally written for the qwen3.6 sub-test
(`scripts/run_thesis_n20_qwen36.sh`) but has since been
**generalised into `scripts/run_cross_model_pilot.sh`** — a
model-agnostic driver that accepts `MODEL`, `LABEL`, `N`,
`OUTPUT_DIR_NAME`, and `FORCE` as env vars. The original
qwen36 script is now a thin deprecation shim that just sets
the historical defaults and delegates.

| Artefact | Path |
|---|---|
| Model-agnostic driver | `scripts/run_cross_model_pilot.sh` (use for new model runs) |
| Legacy qwen36 shim | `scripts/run_thesis_n20_qwen36.sh` (back-compat only) |
| Per-project results | `real_test_cases/<proj>/results_compare_runs_<LABEL>_n<N>/run_comparison_*/multi_run_report.json` (default; overridable via `OUTPUT_DIR_NAME`) |
| Cross-family wrapper | `scripts/run_cross_family_n10.sh` (chains gemma4 + mistral-small3.2 in sequence) |
| Cross-model meta-analysis | `scripts/cross_model_comparison.py` |
| Sub-test results doc | `docs/sub_test_qwen36_results.md` (generated by `cross_model_comparison.py`) |

The qwen3.6 sub-test specifically uses `LABEL=qwen36` and the
output dir `results_compare_runs_thesis_n20_qwen36` (legacy
name from before the parameterisation). Newer sub-tests use
the default naming convention `results_compare_runs_<LABEL>_n<N>`.

## 5. How to run

From `secreqgen/`:

```bash
# 1. Verify Ollama has the model and it produces valid JSON output:
curl -s -X POST http://localhost:11434/api/generate \
  -d '{"model":"<MODEL_TAG>","prompt":"Output JSON only: {\"x\":1}",
       "stream":false,"format":"json","think":false,
       "options":{"temperature":0.0,"num_predict":50}}' \
  --max-time 60 | python3 -m json.tool | head

# 2a. Run a single-model sub-test (any Ollama model). The default 4-project
#     subset (mastodon, mattermost, bitwarden, keycloak) is used if no
#     positional args are passed:
MODEL=gemma4:26b              bash scripts/run_cross_model_pilot.sh
MODEL=mistral-small3.2:24b    LABEL=mistral_small_32  bash scripts/run_cross_model_pilot.sh
MODEL=qwen3.6:latest          LABEL=qwen36_latest      bash scripts/run_cross_model_pilot.sh

# 2b. Or run the cross-family wrapper (gemma4 → mistral-small3.2 in sequence):
bash scripts/run_cross_family_n10.sh

# 2c. Or use the legacy qwen36 shim (preserves historical qwen36 defaults
#     for back-compat with docs/scripts that reference it):
bash scripts/run_thesis_n20_qwen36.sh

# Run only a subset of projects:
MODEL=gemma4:26b  bash scripts/run_cross_model_pilot.sh keycloak mastodon

# Force redo a previously-completed project:
FORCE=1  MODEL=gemma4:26b  bash scripts/run_cross_model_pilot.sh keycloak
```

After the run completes:

```bash
# Cross-model comparison (covers all models present on disk)
PYTHONPATH=src .venv/bin/python scripts/cross_model_comparison.py \
    --output docs/sub_test_qwen36_results.md
```

## 6. How to read the result

The sub-test produces three kinds of evidence:

### 6.1  Direction-of-effect agreement table

For each subset project, are the per-run verdicts (STRONG +,
moderate +, null, moderate −, STRONG −) the **same** under both
models? The summary appears in
`docs/sub_test_qwen36_results.md`.

* **All 4 agree → strong evidence** that per-project verdicts
  generalize across base models. The n20 baseline result is
  trustworthy beyond its single-model context.
* **3 of 4 agree (1 shifts)** → mostly generalises; document the
  exception and its likely cause (probably a baseline-floor change).
* **2 or fewer agree** → the n20 baseline result is partially
  model-specific. The thesis claim must be re-narrowed to "under
  qwen3 specifically" until further model variants are tested.

### 6.2  Baseline-floor comparison

Does the stronger model raise the absolute baseline F1 across all
4 projects?

* **Yes, uniformly** → the "stronger LLM = less RAG headroom"
  hypothesis is supported. The thesis can claim that RAG benefit
  measurement is itself a function of base-model capability.
* **No / mixed** → the relationship between base-model strength
  and RAG headroom is more complex than a simple ceiling effect.

### 6.3  Δ-of-Δ analysis

For each project, compute `Δ_qwen3 = (RAG_F1 − baseline_F1)`
under qwen3, and the same under qwen3.6. The difference of those
differences is the RAG-benefit-shift attributable to the model
swap.

* **Per-project Δ-Δ ≈ 0** → RAG benefit is project-intrinsic.
* **Per-project Δ-Δ → 0 with stronger model** → RAG ceiling effect.
* **Per-project Δ-Δ flips sign** → the model swap fundamentally
  changed what RAG does on that project.

## 7. What this sub-test does NOT claim

* It does not claim that `qwen3.6:35b-a3b-coding-mxfp8` is "the
  best" model for security requirements generation. The choice
  is one variant from one family.
* It does not claim that 4 projects exhaust the cross-model
  variance space. Larger model studies are explicit future work.
* It does not change the **main thesis claim**, which remains:
  *the multi-run paired-statistics methodology reliably
  identifies, at the per-run sensitivity level, where RAG helps
  versus hurts.* The sub-test adds a **scope qualifier** —
  whether that identification is itself model-invariant.
